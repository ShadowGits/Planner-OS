# ASAP category and Apple Reminders

User requested a persistent ASAP strip, four-hour distinct reminders, the requested
initial items, and completion synchronization with their chosen Apple Reminders
list. User also requires one final screen session: no GUI automation, privacy
prompts or app installation during preparation.

## Storage and queries

ASAP uses existing task metadata (`asap: true`), retaining normal task identity,
completion and tenant scope. No existing priority is repurposed and no existing
rows are rewritten. Three user-requested tasks are now in the live workspace; an initially
misinterpreted split item was corrected by renaming its retained record and
removing only the extra record.
Titles and credentials are deliberately excluded from this log and migrations.
No emails were sent. Native app integration is not yet installed.

Inbox responses add optional `asap_items`, a strict, tenant-filtered projected
query of open ASAP tasks across dates. Existing clients ignore this additive
field; older servers omit it and new clients retain existing notifications.
The query reads IDs, titles, status, scheduling basics and creation time only.
There is no new poll loop, server reminder job, full-planner download or broader
projection of ordinary tasks. The additive partial index in migration 0037
is prepared, not applied. Category storage works with the existing schema.

This new category intentionally adds one narrow database select to existing
Inbox refreshes; the REST client's completeness pagination may make a data and
empty-page request. It does not add an app-to-Cloud-Run request per refresh.
The CPU impact needs production measurement; monthly 60/70% targets remain
unchanged and are not certified by tests.

## Notifications and Apple Reminders

One stable local repeating notification uses a distinct three-pulse bundled
sound, title/category/thread, and a 14,400-second interval. Its generic ASAP
body stays stable so ordinary refreshes or edits cannot postpone its timer.
Removing the last open ASAP item removes its pending and delivered notification
when the confirmed inbox snapshot is reconciled, independently of the normal
seven-day feed succeeding. Normal task and daily alerts
remain. Existing 58 normal slots plus daily alerts and one ASAP slot remain
below Apple's pending-request ceiling. Notification permission/settings apply.

Apple Reminders is opt-in using the strip's connect button. Full Reminders
permission is requested only by that explicit action, never a background read.
The requested list name is configured in the bridge. Only reminders tagged
with a task UUID and a connection-scoped fingerprint are reconciled. Unrelated
list entries are untouched; duplicate named lists and read-only calendars
produce errors rather than silently selecting another list. The existing list
must be available; a missing or unsynced list never creates a duplicate list.

Closing in Apple Reminders closes the existing Planner task through its normal
confirmed write path; closing in Planner marks the matching reminder complete.
Completion wins concurrent changes. This is completion synchronization, not a
bidirectional title/date editor or a reopening protocol. A device only marks
missing tasks complete if it previously observed them open, preventing a stale
snapshot from closing a reminder another device just created. Failed reads keep
existing data. Account/connection changes are checked before Planner writes.
