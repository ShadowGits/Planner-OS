# Mac habit save returned HTTP 500

## Production evidence

The user's Mac reported HTTP 500 after the preceding Cloud Run HTTP 503 outage.
The failing request started at 2026-11-27 18:29:49 UTC (23:59:49 IST).
Cloud Run revision `planner-os-api-00304-6k9`, build commit `5aac7ca`, logged:

```text
PATCH /v2/day/tasks/habit:[redacted]:2026-11-27 -> HTTP 500
patch_day_task -> reschedule_occurrence -> _upsert_override -> insert_row
SupabaseError: Supabase request failed with HTTP 409
```

The same occurrence received successful PATCH responses immediately before
and after this failure. A subsequent read found exactly one override belonging
to the configured user. No production task content or credentials were saved.

The server was reachable: health and the web shell returned HTTP 200. Six
authenticated, read-only checks also returned HTTP 200 with `success=true`:
day views for November 27 and 28, inbox, week, projected project names, and
projected milestone labels. These reads do not validate every mutation.

The confirmed failure is an unhandled database insert conflict. The schema has
a unique index on `(habit_id, on_date)`, while the service reads and then inserts
in separate requests. A competing first save can therefore cause this failure.
The original database error body/constraint name was not retained, so the logs
alone do not prove which competing write or constraint caused the incident.

## Change

Keep the existing projected, tenant-scoped lookup and normal insert/update path.
If inserting an override returns HTTP 409, perform one strict lookup of that
exact habit and rule date within the current tenant. If the override exists,
apply only the caller's patch to that row. Preserve independently saved star,
skip, time and duration fields; do not apply insert defaults to an existing row.

If the lookup fails, no row is visible, or the insert failed with another
status, propagate the error. Never turn a failed read into an empty snapshot,
retry inserts blindly, or update another tenant's override.

This recovery covers the reproduced conflicting-first-save case. It does not
claim every possible database 409 is repaired. There is no database migration,
Apple source change, polling change, extra routine query, or retention change.
Extra database work is limited to a conflicting user-initiated save. The
five-minute reminder cadence and monthly cost targets remain unchanged; local
tests do not prove monthly production usage.
